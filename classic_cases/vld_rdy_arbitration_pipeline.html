多路 VLD/RDY 请求仲裁的流水化问题与改进方案

分析仲裁结果寄存一拍后可能出现的过期 RDY 与空闲周期，并讨论请求缓存、Pending 状态和流水仲裁的改进方向。

1. 问题背景

多路输入源通过 VLD 表示请求/数据有效，仲裁器选择其中一路，并通过对应的 RDY 表示本拍是否接收该请求。

标准握手条件：

FIRE[i] = VLD[i] & RDY[i]

只有 VLD 和 RDY 在同一个时钟周期同时为高，该请求才算完成一次握手。

1.1 组合式仲裁

组合式仲裁需要在当前周期内，根据当前各路 VLD 产生对应 RDY。请求路数较多、仲裁逻辑较复杂时，VLD → RDY 组合路径可能成为时序瓶颈。

2. 直接将仲裁结果打一拍的问题

为了缩短组合路径，可以将仲裁结果寄存一拍：

VLD(t) → Arbiter → RDY(t+1)

核心风险：上一拍参与仲裁的请求，可能已经在上一拍完成握手。如果仲裁器没有正确处理这次握手，下一拍就可能输出一个过期的 RDY。

2.1 两路请求示例

假设 A、B 两路在 C0 时 VLD 都为高，当前已有的仲裁结果选择 A，因此 A 在 C0 完成握手。如果仲裁器在 C0 仅根据当前 VLD 计算下一拍结果，没有考虑 A 在 C0 已经完成握手，就可能再次选择 A。

信号C0C1C2
A_VLD100
A_RDY110
A_FIRE100
B_VLD111
B_RDY001
B_FIRE001

2.2 时序示意

  1. C0：A、B 都有请求，当前授予 A，A 完成握手。
  2. C0 时钟边沿：如果下一拍仲裁只看到了 A_VLD=1，却没有正确处理本拍 A_FIRE=1，就可能再次把 A 选为下一拍目标。
  3. C1：A 已撤销 VLD，但 A_RDY 仍为高；B 仍有效，却没有获得 RDY。
  4. C2：仲裁器重新选择 B，B 才完成握手。
过期的仲裁结果占用了一个周期，使仍然有效的请求不能及时被接收。实际波形取决于 RDY 寄存器更新方式、仲裁指针更新时机，以及输入端是否允许连续请求。

3. 问题本质

问题本质是：仲裁结果与请求状态发生了一个周期的错位。

  • 哪些请求已经被接收：VLD & RDY。
  • 哪些请求仍然等待处理。
  • 输入源是否会在下一拍继续提供新的请求。
  • 仲裁结果对应的是哪一笔请求，而不只是哪个输入通道。
标准 VLD/RDY 协议下，如果 VLD=1 且 RDY=0，发送端必须保持 VLD 和 DATA，直到握手完成。如果输入端发送的是单拍脉冲，则需要先捕获请求，不能直接套用标准 VLD/RDY 的假设。

4. 改进方案一：请求缓存与仲裁解耦

将“输入请求接收”和“请求仲裁/输出”分开。输入请求一旦被 Buffer 接收，就不再依赖原始输入 VLD 是否继续保持。

4.1 输入侧握手

IN_FIRE[i] = IN_VLD[i] & IN_RDY[i]

输入 RDY 可以根据 Buffer 是否有空间产生：

IN_RDY[i] = Buffer_Available[i]

如果 Buffer 支持同拍出队和入队，可以在旧请求被取走的同一周期接收新请求。具体输入 RDY 逻辑需结合 Buffer 深度和实现方式确定。

4.2 仲裁侧

ARB_REQ[i] = Buffer_Valid[i]

仲裁器只观察 Buffer 中保存的有效状态。选中某个 Buffer 后，读取其中保存的 DATA 和 ID，并在对应请求被正式取走时更新 Buffer 状态。

4.3 输出侧握手

OUT_FIRE = OUT_VLD & OUT_RDY

当 OUT_VLD=1 且 OUT_RDY=0 时，输出端必须保持 OUT_VLD、OUT_DATA 和 OUT_ID 稳定，直到完成握手。

输入侧请求接收与输出侧仲裁/发送解耦后，仲裁可以增加流水级，而不会因为原始输入 VLD 撤销导致请求丢失。

5. 改进方案二：不增加 Buffer，只修正仲裁状态

如果每路输入最多只允许存在一个未完成请求，可以考虑使用 pending 状态保存请求。

  • 捕获尚未处理的请求。
  • 请求被正式接受后，清除对应 pending 状态。
  • 仲裁器只对尚未处理的请求进行选择。
// 示意代码：实际更新条件需要结合接口协议设计
if (request_captured)
    pending[i] <= 1'b1;

if (request_accepted)
    pending[i] <= 1'b0;
如果同一路输入允许连续产生多笔请求，而前一笔尚未处理完成，单个 pending bit 无法保存请求数量，需要 FIFO 或计数器。如果输入端可以连续每拍提供新数据，也不能简单地在一次 FIRE 后将该输入屏蔽一拍。

6. 三种方案对比

方案能否避免过期仲裁结果吞吐率潜力主要代价
直接将 RDY 打一拍不能自动保证可能出现空拍最低
修正 pending / FIRE 状态可以，但依赖输入协议和状态管理较高控制逻辑更复杂
Input Buffer + 流水仲裁可以解耦可设计为每拍接收/输出一个请求Buffer、反压和流水控制
吞吐率注意：流水仲裁并不天然保证每拍一个请求。要达到每拍一个请求，需要每一级都能每拍接收一个新仲裁任务、流水线不因下游反压而停顿，并且 Buffer 的入队/出队能力满足吞吐要求。如果仲裁器本身每4拍才完成一次选择，那么吞吐率仍然只有每4拍一次。

7. 推荐设计方向与检查项

建议优先评估：输入请求捕获 → Pending Buffer → 多级流水仲裁 → 输出 VLD/RDY。

  1. 请求接收后必须可靠保存，不能因为原始 VLD 撤销而丢失。
  2. 仲裁器只对尚未处理的请求进行选择。
  3. DATA、ID、CHANNEL_GNT 必须保持对应关系。
  4. 下游未接收时，输出 VLD、DATA、ID 必须保持稳定。
  5. Buffer 应支持必要的同时入队、出队操作，避免连续请求产生不必要的气泡。
  6. 明确仲裁指针在“产生选择结果”“请求被缓存接收”还是“输出握手完成”时更新，避免重复选择或跳过请求。
  7. 根据实际 STA 报告决定流水级数，不必预先固定为4拍。
最终结论：当前架构不要求输入请求当拍完成仲裁，因此没有必要强迫 VLD → RDY/GNT 保持一条很长的组合路径。更合理的思路是先保证请求被可靠捕获，再允许仲裁分多拍完成。这样可以用适当的响应延迟换取更好的时序，同时通过流水化和 Buffer 设计尽量保持吞吐率。

8. 需要进一步确认的接口条件

类型行为设计要求
A：标准 VLD/RDYVLD=1 且未握手时，发送端保持 VLD 和 DATA可通过输入 Buffer 接收并反压
B：单拍脉冲VLD 只持续一拍，不等待 RDY必须在脉冲到来时捕获请求，必要时使用 FIFO
C：电平请求业务未完成时持续保持，收到 GNT 后撤销需要明确 GNT 的接受语义及重复请求处理
在确认 A/B/C 之前，不应直接确定 Buffer 深度、请求保持方式和仲裁状态更新时机。
